# Payments and receipts

## Backend

**Payments** (`billing.Payment`) are money received against one bill (amount > 0, two places; paid date not after the property's `business_date()`, any earlier date; notes ≤ 500, trimmed). The tenancy and property come through the bill, never stored on the payment. Totals are always derived from the **effective** payment records, those not reversed (`Payment.objects.effective()`, `calculations.total_paid_for` / `entry_amounts`, `RentEntry.objects.with_amounts()`): see [Corrections](#corrections-reversing-a-payment).

- **Every payment is created by `billing/services.py` `record_payment`**, inside a transaction that locks the bill (`select_for_update`), rechecks access, then checks the idempotency key **before** the balance (so a retry of the payment that settled the bill still succeeds), then refuses more than the outstanding (409 `payment_exceeds_outstanding` with `outstandingAmount`).
- While it holds that lock it numbers the payment on its bill (`sequence`: 1, 2, 3…; unique per bill, from 1). That's the durable record of the order payments were recorded in: receipts and the payment list use it, never `created_at`, which can tie or run backwards with the clock. Migration `0005` numbered existing payments by `created_at`, then id.
- Each request carries an `Idempotency-Key` header (a UUID, required): the same key, bill, person and validated details returns the existing payment (200); anything else with that key is 409 `idempotency_conflict`. The unique key constraint is the last guard (the same key on two bills locks two rows): only that constraint, matched by name, is mapped, and looked up outside the failed transaction.
- API: `.../entries/{entryId}/payments/`. POST records (201, or 200 for a retry) and returns `{payment, entry}` with the bill's current balance; GET lists them newest paid date first (the same day, latest recorded first), unpaginated.
- No update or delete; payments are view-only in admin, so nothing bypasses the service. A mistake is reversed and replaced ([Corrections](#corrections-reversing-a-payment)).
- Payments carry `status` (`recorded` or `reversed`) and `reversal: {id, reason, createdAt, createdByName}` or `null`, loaded in the list's own query. A retry of a payment reversed since returns it as it is now, reversed (200): never recorded again, never counted again.
- A bill can be created with an initial payment through the same service ([rent-entries.md](rent-entries.md)).

## App

Payments (`types/payment.ts`) are recorded through `services/payment.service.ts` (`recordPayment`, `getPayments`, `reversePayment`; decimal strings out, validated `PaymentDto`s in). On the details page Record payment opens `RecordPaymentForm` in a `Dialog` (a local preview of the remaining balance; the backend checks again), and `stores/rentEntry.ts` `addPayment` shows the **backend's** returned balance wherever the bill appears (cache, history page, dashboard summary), then reloads the bill's payment history (`loadPayments`, keyed by bill id; a failed load is an error with Retry, never "No payments"). An overpayment conflict refreshes the bill so the preview shows the current outstanding.

### Retries never record money twice

Pages own the idempotency key: `NewRentEntryView` one per bill; for payments the store keeps one per bill (`paymentKeyFor`), so closing the dialog or leaving the page keeps it, and the details page can't be left, nor the dialog closed, while a payment save is in flight.

- One key per intended operation, kept after an **uncertain** failure (`isUncertainFailure`: no response, 5xx, unreadable response; the error's `uncertain` flag) so saving again is a retry the backend recognises, and replaced after a success or a definite rejection (a 429 is definite: nothing was done).
- Editing the form between attempts is still safe: if the first attempt was saved, the changed request conflicts (`idempotency_conflict`, shown with the saved record) instead of saving a second one.
- A retry the backend answers with the existing payment says it "was already recorded".

## Receipts

A receipt confirms **one payment**: a ₹3,000 payment against a ₹15,750 bill gets a ₹3,000 receipt, which also shows the bill as it stood right after that payment, so it never implies the bill is paid.

### Backend

`billing.Receipt` is a snapshot, in explicit columns, of everything printed on the receipt: the issuer (the property's name, address and contact number; as **received by**, whoever **recorded** the payment, since they took the money; and as **authorized by**, whoever issued the receipt, so an owner issuing one for a manager's payment shows both. Imported payments name the importing admin as both. Migration `0010` copied each earlier receipt's received-by name, which was its issuer's, as its authorized-by, so those print as before), the tenancy (name, flat, mobile, deposit, rent due day), the bill's charges and electricity amount, its total due, paid **up to and including this payment** (the bill's payments with a `sequence` up to its own) and outstanding after it, what the previous month's bill still owed when it was issued, and the payment's amount, date and notes. It's never rebuilt from today's records: later payments or changed tenancy or property details never change it.

- **One per payment**, enforced by the database (`payment` is a unique one-to-one, `PROTECT`ed). The reference reads like the owners' receipt names, `Tenant_Name_Flat_Rent_Month YYYY` from the tenancy and billing month (`Shaik_Zahid_Ali_202_Rent_October 2026`, `models.receipt_reference`), with `_2`, `_3`… for the property's later receipts with the same name, flat and month (a bill's later payments, or two tenancies of the same name in one flat that both cover the month). It's set once when issued (renaming the tenant later never changes it) and is also the PDF's file name. References are unique **per property** (the receipt saves its `property`; `unique_receipt_reference_per_property`), so another property's tenant with the same name, flat and month never changes this one's number. Issuing locks the bill, then the payment, then the tenancy, then the property (the last two `FOR NO KEY UPDATE`, so new tenancies and bills aren't held up), and reads each again under its lock before checking or copying anything: a tenant rename or address edit that commits while a receipt waits is on that receipt, never the details from before it. The property's lock also numbers its receipts one at a time, so the number is always free and nothing is retried. Migration `0006` copied each existing receipt's property. Undoing it makes references unique across every property again, so the rollback stops with the references two properties share rather than renumber receipts already printed (`refuse_shared_references`); it only runs while none are shared.
- **Every receipt is created by `billing/services.py` `issue_payment_receipt`**, inside a transaction that locks the bill, then the payment (`select_for_update`; the same order as reversal), rechecks access (`ISSUE_RECEIPTS`), returns the payment's existing receipt, void or not, **before** validating today's details (so an issued receipt reopens even if the address was cleared since), refuses a reversed payment without one (409 `payment_reversed`), then requires the property's name and address and the tenant's name and flat (400 `receipt_configuration_incomplete`, its `detail` saying what to set) and copies the snapshot. The unique column is the last guard: only that constraint (`billing_receipt_payment_id_key`, matched by name) is mapped, outside the failed transaction. A failure saves nothing and leaves the payment as it was.
- API: `.../payments/{paymentId}/receipt/`. POST (empty body) issues it (201) or returns the one already issued (200), so no idempotency key is needed; GET returns it, or 404 if none was issued (it never issues one). The property, tenancy, bill and payment are each looked up only within the one before (`ScopedLookupMixin` in `billing/views.py`, shared with the bill and payment views), so another bill's payment is 404.
- Payments carry `receipt: {id, reference, status}` or `null`, loaded in the list's own query. A receipt's `status` is `issued` or `void`; a void one also has `voidedAt` and `voidReason`.
- A receipt's paid-to-date counts the payments up to its own that weren't reversed when it was issued.
- No update or delete; receipts are view-only in admin (searchable by reference, tenant and flat). That isn't database-level immutability: keep receipt writes in the service. The only change ever made to one is voiding, by `reverse_payment`.

### App

`services/receipt.service.ts` (`issueReceipt`, `getReceipt`; validated `ReceiptDto`s mapped to `types/receipt.ts` `PaymentReceipt`, money as numbers). On the details page `PaymentHistory` (its `receipts` prop on) offers **Issue receipt** for a payment without one and **Download receipt** once it has one. Either way `stores/rentEntry.ts` `getReceipt(tenantId, payment)` gets the snapshot (GET when the payment has a receipt, otherwise POST; only void receipts are cached, by payment id, since a void one never changes again while an issued one can be voided by a reversal made elsewhere) and marks the payment as having one, then the page downloads it as a PDF (`utils/receiptDownload.ts`: jsPDF and Poppins, laid out by `utils/receiptPdf.ts` from `utils/receiptContent.ts`, which reads only the snapshot and recalculates nothing).

- Wherever a bill's **View bill** is offered (the dashboard's latest bill, `LatestEntryCard`, and each row of the tenant's bills, `RentEntryHistory`), a paid bill (anything paid) also offers **Download receipt**: the receipt for its most recent payment (newest paid date, then newest recorded), issued if it has none (`getLatestReceipt`, which always reloads the bill's payments first, never trusting a loaded list that may predate someone else's payment, and fails visibly if they can't be loaded). Its other payments' receipts are on the details page.
- Every page downloads through `composables/useReceiptDownload.ts` (`downloadPaymentReceipt`, `downloadLatestReceipt`): one download at a time, its id in `downloadingId`, the problem in `error`, shown inline above the card or table. Pages call `reset()` when they show other bills (another tenant or bill, or the history's filters and pages): a download under way still finishes, but its error and wait don't carry over. Reopening an issued receipt that gets no response just says to try again; only issuing says it couldn't confirm whether one was issued.
- Every receipt button is disabled while one is being prepared ("Preparing…").
- A void receipt is offered as **Download void receipt**; a reversed payment without one gets none. An issued receipt is always fetched again rather than reused, so one voided since, here or elsewhere, downloads as void even when the loaded history still says it's issued. Issuing for a payment reversed since the history loaded (409 `payment_reversed`) says so and reloads the bill and its history. The bill-level **Download receipt** uses the latest payment that still counts.
- A failure throws `ReceiptError` and never changes the payment. A lost response is `uncertain`: trying again is safe, since the backend returns the receipt it already issued. A refusal shows the backend's reason (e.g. the property's address isn't set). If only the PDF fails, the page says the receipt is issued and to try again.
- Nothing claims the file was saved: the browser decides that.

## Corrections: reversing a payment

A payment recorded by mistake (the wrong amount, date or bill) is **reversed**, then its replacement is recorded as a new payment. The original stays, unchanged, in the history; editing it would make it and its receipt misleading. Reversing is an accounting correction in the app: no money is moved or refunded.

| Mistake                        | Correction                                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------------- |
| Wrong payment amount or date   | Reverse it, then record the replacement                                                            |
| Payment against the wrong bill | Reverse it, then record it against the correct bill                                                |
| Wrong bill charges             | Reverse its payments, then **Correct bill** ([rent-entries.md](rent-entries.md#correcting-a-bill)) |
| Wrong receipt details          | Not yet: void and reissue needs its own workflow                                                   |

### Backend

- `billing.PaymentReversal`: one per payment (a unique, `PROTECT`ed one-to-one), with a required `reason` (≤ 500, trimmed; a check constraint refuses an empty one), `created_by` and `created_at`. Full reversals only: the amount reversed is always the payment's. A reversed payment stops counting everywhere a total is worked out: bill figures, list annotations and the `?payment_status=` filter, overpayment checks, initial-payment and retry responses, new receipts' snapshots, the legacy import and `ledger_summary`. So a paid bill can become partially paid or unpaid again.
- **Owners and managers reverse** (`Capability.REVERSE_PAYMENTS` in `properties/roles.py`; voiding or correcting a bill stays owners-only): a role without it gets 403, someone without access to the property 404. Checked in the view and again inside the service's transaction.
- **`billing/services.py` `reverse_payment(payment_id, actor, reason)`**, in one transaction: locks the bill, then the payment (the order receipt issuance takes, so the two never race or deadlock), rechecks the actor's access, returns an existing reversal when the reason matches (another reason is `ReversalConflictError`), creates the reversal, voids the payment's receipt, and returns the bill's figures without the payment. Any failure saves neither the reversal nor the voiding. The unique column is the last guard (`billing_paymentreversal_payment_id_key`, matched by name, looked up outside the failed transaction).
- **Voiding** sets the receipt's `voided_at`, `voided_by` and `void_reason` together (a check constraint requires all or none) and nothing else: its reference and snapshot stay as issued. Issuing again returns it, void. PDFs downloaded before can't change; looking the receipt up always gives its current status.
- API: `POST .../payments/{paymentId}/reversal/` with `{"reason": "..."}` (unknown fields refused): 201 with `{payment, entry}` (the payment, reversed, and the bill's balance), 200 for a retry with the same reason, 409 `reversal_conflict` for another reason. No idempotency key: the payment identifies its only reversal.
- Read-only in admin (Payment reversals; payments and bills show "Reversed (not counted)"; receipts show their void details). Corrections go through the app, so who, when and why are always recorded; no signals, the transaction does it all.
- Migration `0008` added these. Undoing it stops while any reversal or void receipt exists (`refuse_corrections`): the reversed payments would count again.

### App

On the details page, owners and managers (`accessStore.selectedProperty.role`) get **Reverse** on each payment that still counts. It opens `ReversePaymentForm` in a `Dialog`: the tenant, billing month, the payment's date and amount, what reversing does (a receipt it has becomes VOID, copies already shared can't be recalled, no money is refunded), and a required reason (`validateReversalReason`, as the backend checks). `stores/rentEntry.ts` `reversePayment` shows the **backend's** returned balance wherever the bill appears and the payment as reversed, and reloads the history; on failure the dialog keeps the reason. As with a payment save, the page can't be left, nor the dialog closed, while it's in flight. A lost response says to try again with the same reason (safe: the payment has one reversal) and reloads the bill and its history, so they show the reversal if it went through. A `reversal_conflict` refreshes the bill to show the reversal someone else made.

After a reversal the page offers **Record replacement payment**: the usual Record payment dialog, empty (never the reversed amount), with a new idempotency key.

`PaymentHistory` keeps reversed payments, muted, with the amount struck through, a **Reversed** label and "Reversed by … on …: reason"; a note says they don't count towards Total paid. A void receipt's PDF (`utils/receiptContent.ts`, `utils/receiptPdf.ts`) prints **VOID — Payment reversed** in a red box above everything else, with when and why, a faint VOID across each page, status VOID, and ` (VOID)` in its file name; the snapshot is otherwise printed as issued.

The owners' current receipts come from the Google Sheet's Apps Script ([google-sheets-integration.md](google-sheets-integration.md)).
