# Sign-in and property access

## Sign-in (app)

Sign-in is **Google, through Firebase Authentication** (`services/auth.service.ts`, the only module importing `firebase/auth`; the app is created lazily in `services/firebase.ts` from `VITE_FIREBASE_*` in `.env.local`). Firebase keeps the session itself and restores it **asynchronously**: `authStore.init()` subscribes once and resolves on the first auth state, `ready` says it has, and the route guards `await` it before deciding. Missing config leaves the app signed out with `loginNotice` shown on login. Google sign-in is free on Firebase; the phone OTP it replaced paid per SMS.

`LoginView` is one **Continue with Google** button (`components/auth/GoogleSignInButton.vue`). It calls `signInWithPopup` straight from the click (browsers block popups opened later) and always asks which account (`prompt: select_account`), so a shared device doesn't sign in the wrong person. Closing Google's window is `cancelled` and shows nothing; a blocked popup, a disabled account or a setup problem is explained under the button. Firebase errors map to `AuthErrorCode` (`services/authErrors.ts`) and the store words them; an outage is never shown as a refusal. There's no redirect fallback: without Firebase's `/__/auth/*` pages served from the app's own domain, redirects fail in Safari. `App.vue` watches the auth user: if Firebase ends the session elsewhere (another tab, disabled account) it clears per-user state and leaves protected pages.

Phone numbers are contact details only now (people's, properties', tenants'): stored as E.164 (`+918341413827`), formatted for display only (`utils/phone.ts`). The accepted countries (India, Australia, US) live in one table, `utils/phoneCountries.ts`, mirrored by the backend's `accounts/phone.py` (change both).

`AppLayout` puts the logo and the account menu (`components/access/UserMenu.vue`) on the backdrop above the card, on every signed-in screen. The menu shows the person's `name` from `/me` with their initials and their Google email under it (the email when no name is set, or Firebase's until `/me` answers, so logout is always there) and holds **Switch property** (with several properties, except on the property page) and **Logout**. The layout wires it to the stores and router itself, so views don't. Inside the card, a row holds a screen's way back on the left (`#back` slot) and its main control centred (`#toolbar`, the dashboard's tenant search).

Logout (`composables/useLogout.ts`) clears the selected tenant, property access and the bills loaded from the backend, then `signOut()`s.

**Inactivity timeout** (`composables/useInactivityTimer.ts`, mounted in `App.vue`): the session ends after 15 minutes of no user activity (no mouse, keyboard, scroll or touch events on `window`). Activity events reset the countdown; resets are throttled to once per second. On expiry the user is fully signed out via `useLogout` and `loginNotice` is set so the login page explains why. The timer only runs while `authStore.isAuthenticated` is true.

## Sign-in (backend)

- `AUTH_USER_MODEL` is `accounts.User` (`AbstractUser` + nullable unique `firebase_uid`, a unique `email` and an optional contact `phone_number`). Roles belong on property membership, never on the user.
- Auth is Firebase ID tokens (`Authorization: Bearer`) verified in `accounts/firebase.py`, the only module that imports `firebase_admin`; it raises its own `InvalidFirebaseTokenError` (→ 401) or `FirebaseUnavailableError` (→ 503, never reported as a bad login). Never trust a UID or email from the request body. Admin keeps Django's session login.
- **Sign-in is invite-only.** A person (`accounts.User`, "People" in admin, with one optional `name` field rather than first/last names, displayed as "Name — +91 …", else their email) is invited when an admin adds them with their **Google email** (required on the add form; unique ignoring case, stored lowercased). Admin doesn't call Firebase to invite: the person's **first Google sign-in links them** (`accounts/services.py` `get_registered_user`). The token is matched by UID first; with no person linked to it, it links the invited person whose email it carries, only if the sign-in provider is `google.com`, Google has verified the email (`email_verified` is `true`), and that person isn't linked yet. From then on only the UID is matched, even if the Google account's email changes. Anything else gets 403 `not_registered` and creates nothing.
- **Ending sign-in:** changing or removing a linked person's email in admin unlinks them and revokes their Firebase sessions (`unlink_if_email_changed`, the last step of the admin save, inside its transaction: if Firebase is unreachable nothing is saved). The API also refuses anyone without an email, so an older token stops working. Making the person inactive blocks them too.
- **The move from phone sign-in** (migration `accounts.0005`) set each person's phone identity aside in `legacy_phone_firebase_uid` and cleared `firebase_uid`, so everyone links again at their first Google sign-in; reversing the migration puts the phone identities back. The column is temporary: drop it once everyone has signed in with Google ([deployment.md](deployment.md), "Moving to Google sign-in").

## Property access

**Signing in is not access.** Access comes only from an active `PropertyMembership` of an active `Property`, granted in admin (which records `granted_by`). Memberships are ended (inactive), never deleted. Admin portal access (`is_staff`) and app sign-in are separate permissions on one person; admins get no API access without a membership. Granting access is manual (backend README "Granting access"): sign in once, then add an owner membership in Django admin.

`GET /api/v1/me/` answers the person's `id`, `name` (empty when unset), `email`, `phoneNumber` (empty when unset) and their `properties`. In the app: if it answers 403 `not_registered`, the access store ends the Firebase session (`authStore.endSession`) and login explains why. `stores/access.ts` holds the identity and the selected property: one property is selected automatically, several need a choice, none means "no property access", and a failed load is an **error with Retry**, never no access. Property selection is separate from tenant selection.

## Route guards

Route guards live in `router/index.ts` (`meta.requiresAuth`, `meta.guestOnly`, `meta.requiresProperty`) and are async: they wait for `authStore.init()` and, for property routes, `accessStore.load()`. Pinia is installed before the router in `main.ts` so guards can use stores. Routes with `meta.requiresProperty` (dashboard and tenant pages) redirect to `/properties` (`PropertySelectView`, with `?redirect=` to return; only same-app paths are followed) until a property is selected. Guards are UX only: the backend enforces authentication and property access.
