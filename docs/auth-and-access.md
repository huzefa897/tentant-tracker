# Sign-in and property access

## Sign-in (app)

Sign-in is **Google, through Firebase Authentication** (`services/auth.service.ts`, the only module importing `firebase/auth`; the app is created lazily in `services/firebase.ts` from `VITE_FIREBASE_*` in `.env.local`). Firebase keeps the session itself and restores it **asynchronously**: `authStore.init()` subscribes once and resolves on the first auth state, `ready` says it has, and the route guards `await` it before deciding. Missing config leaves the app signed out with `loginNotice` shown on login. Google sign-in is free on Firebase; the phone OTP it replaced paid per SMS.

`LoginView` is one **Continue with Google** button (`components/auth/GoogleSignInButton.vue`). It calls `signInWithPopup` straight from the click (browsers block popups opened later) and always asks which account (`prompt: select_account`), so a shared device doesn't sign in the wrong person. Closing Google's window is `cancelled` and shows nothing; a blocked popup, a disabled account or a setup problem is explained under the button. Firebase errors map to `AuthErrorCode` (`services/authErrors.ts`) and the store words them; an outage is never shown as a refusal. There's no redirect fallback: without Firebase's `/__/auth/*` pages served from the app's own domain, redirects fail in Safari. `App.vue` watches the auth user: if Firebase ends the session elsewhere (another tab, disabled account) it clears per-user state and leaves protected pages.

Phone numbers are contact details only now (people's, properties', tenants'): stored as E.164 (`+918341413827`), formatted for display only (`utils/phone.ts`). The accepted countries (India, Australia, US) live in one table, `utils/phoneCountries.ts`, mirrored by the backend's `accounts/phone.py` (change both).

`AppLayout` puts the logo and the account menu (`components/access/UserMenu.vue`) on the backdrop above the card, on every signed-in screen. The menu shows the person's `name` from `/me` with their initials and their Google email under it (the email when no name is set, or Firebase's until `/me` answers, so logout is always there) and holds **Switch property** (with several properties, except on the property page) and **Logout**. The layout wires it to the stores and router itself, so views don't. Inside the card, a row holds a screen's main control centred (`#toolbar`, the dashboard's tenant search).

**Navigation.** Once a property is selected, the layout shows the app's sections (`components/nav/AppNav.vue`): **Home** (the dashboard), **Tenants** (`/tenants`) and a **Quick entry** button, plus **Account** (`/account`, `AccountView`: who is signed in, the property, Switch property and Logout). Both are frosted glass (the `glass` and `glass-on-dark` utilities in `style.css`; solid under `prefers-reduced-transparency`). On a phone (below `sm`) they float in a pill-shaped bar at the bottom (Quick entry in the middle, the page padded so nothing hides behind it, above the iPhone home bar) and the header's account menu gives way to Account; on wider screens Home, Tenants and Quick entry sit in a glass pill in the header, beside the account menu. Each item is a real link (`href` from the router) and a plain click navigates in the app; the route's `meta.section` marks the current one (`aria-current="page"`; every `/tenants/...` page is Tenants). The bar hides while a field has focus and the keyboard is open (the visual viewport has shrunk by more than 150px, allowing for zoom), so it never covers what's typed, and it returns when the keyboard is dismissed even if the field keeps focus; with no keyboard open (a hardware one) it stays. **Quick entry** (`QuickEntryDialog`, the bolt in the middle of the bar and the last item in the header) is an entry point to the existing forms, not a new one: a full-height sheet on a phone, a centred dialog from `sm` up. It asks **what to record** (New bill, Payment, Meter reading), then **which tenant** (the dashboard's search; when opened from a tenant's page, that tenant is offered first), and for a bill only **which month** (a month input, defaulting to the month after the tenant's latest active bill, this month if none; it waits for that bill to load). A **bill** then continues in the sheet, as the New bill form (`RentEntryForm` with its `wizard` prop, so the same fields, calculations and checks, one part at a time): **Rent and utilities** (rent, electricity or meter, water), **Payment** (amount paid, date, notes, with the running summary of total due, paid, outstanding and status), then **Confirm** ("Save this bill?", **Yes, save bill** or **Go back**). Continue checks only its own step. Saving goes through `useQuickBill` (the same one-request-per-save, retry-key and meter wiring as the New bill page) and opens the saved bill, after stepping back over the sheet's history so back returns to where Quick entry was opened; while the request is in flight the sheet stays put (close, back and route changes are refused, except signing out); a month that already has a bill offers **Open saved bill**. Every step after the first has a back arrow in the header (it is the browser's back). Then `AppLayout` (the only one that navigates) pushes the existing page: the tenant's bills (`/tenants/:tenantId/entries`) for a payment, since a payment goes on a bill and is recorded from it, or the tenant's meter with Record reading open (`?record=1`); a tenant without a meter is refused for a reading, with why. The sheet's state is in the URL, one history entry per step: `?quick=start` (what), `?quick=bill|payment|reading` (tenant), `?quick=bill&step=month&quickTenant=<id>` (month), then `&step=charges|payment|confirm&quickMonth=YYYY-MM`. The form stays mounted across those steps, including back to the month step (whose URL names no month; `AppLayout` keeps the draft for that tenant and month), so going back loses nothing; choosing a different month or tenant, or closing the sheet, starts a new bill. Changing the tenant clears the month input until that tenant's default loads, so a stale month is never submitted. The browser's back goes to the step before and then closes it; Escape or the close button steps back over what this visit pushed (or just drops the keys when the sheet was opened by a reload or shared link, so it never leaves the app). A reload keeps its place (a tenant named in the URL is fetched by id when the first search page doesn't hold it), and after choosing a payment or meter reading, back returns to the last step. There are no on-screen back links: the browser's (or the phone's) back goes back, and the nav is always the way home. Dead ends keep a button out (Tenant not found → **Go to tenants**, Bill not found → **Go to bills**, Bill saved → **Go to dashboard**).


Logout (`composables/useLogout.ts`) clears the selected tenant, property access and the bills loaded from the backend, then `signOut()`s.

**Inactivity timeout** (`composables/useInactivityTimer.ts`, mounted in `App.vue`): the session ends after 15 minutes of no user activity (no mouse, keyboard, scroll or touch events on `window`). Activity events reset the countdown; resets are throttled to once per second. On expiry the user is fully signed out via `useLogout` and `loginNotice` is set so the login page explains why. The timer only runs while `authStore.isAuthenticated` is true.

## Sign-in (backend)

- `AUTH_USER_MODEL` is `accounts.User` (`AbstractUser` + nullable unique `firebase_uid`, a unique `email` and an optional contact `phone_number`). Roles belong on property membership, never on the user.
- Auth is Firebase ID tokens (`Authorization: Bearer`) verified in `accounts/firebase.py`, the only module that imports `firebase_admin`; it raises its own `InvalidFirebaseTokenError` (→ 401) or `FirebaseUnavailableError` (→ 503, never reported as a bad login). Never trust a UID or email from the request body. Admin keeps Django's session login.
- **Sign-in is invite-only.** A person (`accounts.User`, "People" in admin, with one optional `name` field rather than first/last names, displayed as "Name — +91 …", else their email) is invited when an admin adds them with their **Google email** (required on the add form; unique ignoring case, stored lowercased). Admin doesn't call Firebase to invite: the person's **first Google sign-in links them** (`accounts/services.py` `get_registered_user`). The token is matched by UID first; with no person linked to it, it links the invited person whose email it carries, only if the sign-in provider is `google.com`, Google has verified the email (`email_verified` is `true`), and that person isn't linked yet. From then on only the UID is matched, even if the Google account's email changes. Anything else gets 403 `not_registered` and creates nothing.
- **Ending sign-in:** changing or removing a linked person's email in admin unlinks them and revokes their Firebase sessions (`unlink_if_email_changed`, the last step of the admin save, inside its transaction: if Firebase is unreachable nothing is saved). The API also refuses anyone without an email, so an older token stops working. Making the person inactive blocks them too.
- **The move from phone sign-in** (migration `accounts.0005`) set each person's phone identity aside in `legacy_phone_firebase_uid` and cleared `firebase_uid`, so everyone links again at their first Google sign-in; reversing the migration puts the phone identities back. If two people share an email ignoring case (nothing prevented it before), it stops before changing anything and names them by id, never by email. Reversing needs the old phone users to still exist in Firebase, so they're kept until the rollback window closes. The column is temporary: drop it when that window closes, then delete the old phone users ([deployment.md](deployment.md), "Moving to Google sign-in").

## Dev login (local development only)

To work locally without Google (or without any Firebase config), sign in as an existing person by email:

1. `backend/.env`: `DJANGO_ENV=dev`. Settings refuse to start with it unless `DJANGO_DEBUG=True` and `DJANGO_ALLOWED_HOSTS` lists only local hosts ([security.md](security.md#14-production-settings-debug-off)).
2. `.env.local`: `VITE_DEV_LOGIN_EMAIL=<email of a person in the database>`, e.g. the one given to `seed_dev_data --email` (backend README). Restart `npm run dev`.
3. The login page shows **Dev sign-in as …** under the Google button.

How it works: `services/devLogin.ts` keeps the email in `localStorage` (only when it matches `VITE_DEV_LOGIN_EMAIL`), and `authService` reports that person as signed in without touching Firebase, sends `Authorization: Dev <email>` from `getAuthorization()` instead of a Bearer token, and ends the session on logout (with any Google session Firebase kept, so a reload doesn't sign back in as it). A dev session the backend refuses (401, e.g. it isn't on `DJANGO_ENV=dev`) is ended and the login page says how to turn dev login on, rather than offering a Retry that can't work. With dev login on and no dev session, Firebase is optional: missing config just leaves the app signed out. The backend's `accounts/authentication.py` `DevAuthentication` (installed only with `DJANGO_ENV=dev`) only answers connections from this machine (a loopback peer address, which a caller can't fake the way it can the `Host` header), so it works with Django and `npm run dev` both on the host, whose proxy connects from `127.0.0.1`, but not with `docker compose --profile app`, where the Vite container connects over the Docker network (use Google sign-in there). It finds the active person with that email, ignoring case, and never creates one: an unknown email is 403 `not_registered`, as with Google. Property access still comes from memberships. In a production build `import.meta.env.DEV` is false, so none of it runs, and without `DJANGO_ENV=dev` the backend answers a `Dev` header with 401.

## Property access

**Signing in is not access.** Access comes only from an active `PropertyMembership` of an active `Property`, granted in admin (which records `granted_by`). Memberships are ended (inactive), never deleted. Admin portal access (`is_staff`) and app sign-in are separate permissions on one person; admins get no API access without a membership. Granting access is manual (backend README "Granting access"): sign in once, then add an owner membership in Django admin.

`GET /api/v1/me/` answers the person's `id`, `name` (empty when unset), `email`, `phoneNumber` (empty when unset) and their `properties`. In the app: if it answers 403 `not_registered`, the access store ends the Firebase session (`authStore.endSession`) and login explains why. `stores/access.ts` holds the identity and the selected property: one property is selected automatically, several need a choice, none means "no property access", and a failed load is an **error with Retry**, never no access. Property selection is separate from tenant selection.

## Route guards

Route guards live in `router/index.ts` (`meta.requiresAuth`, `meta.guestOnly`, `meta.requiresProperty`) and are async: they wait for `authStore.init()` and, for property routes, `accessStore.load()`. Pinia is installed before the router in `main.ts` so guards can use stores. Routes with `meta.requiresProperty` (dashboard and tenant pages) redirect to `/properties` (`PropertySelectView`, with `?redirect=` to return; only same-app paths are followed) until a property is selected. Guards are UX only: the backend enforces authentication and property access.
