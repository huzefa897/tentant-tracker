# Rent Tracker

Vue 3 + TypeScript + Vite frontend for managing tenant rent and utility payments (Saleem Towers, India).
Stack: Vue Router, Pinia (setup stores), Tailwind v4, shadcn-vue (reka-ui), Axios.

## Commands

- `npm run dev` — dev server
- `npm run build` — type-check (`vue-tsc`) + production build. Run it: the dev server does not type-check.
- `npm run lint` — oxlint + ESLint with auto-fix
- `npm run lint:check` — same, no fixes (use for verification/CI)
- `npm run format` — Prettier over `src/` (`npm run format:check` to check only)
- `npm test` — Vitest, single run (`npm run test:watch` to watch)
- `npm run check:conflicts` — dry-run merges of the current branch into `main` and every other open PR's branch (`scripts/check-merge-conflicts.sh`, `--strict` to fail on PR-vs-PR conflicts). Textual conflicts only: a clean merge can still break the build.

Before calling work done: `npm run format && npm run lint:check && npm test && npm run build`. CI (`.github/workflows/ci.yml`) runs the same checks on every PR and push to `main`, plus the conflict check on PRs (fails only on conflicts with `main`; conflicts with other PRs are warnings).

## Backend

Django + DRF + PostgreSQL in `backend/` (setup in `backend/README.md`). The frontend calls it for access (`/me`) and tenants (tenancies); rent entries are still local. PostgreSQL runs in Docker (`docker compose up -d --wait db` from the root, host port 5434); Django runs on the host with pipenv, from `backend/`:

- `pipenv run start` — dev server (`runserver`, port 8000)
- `pipenv run makemigrate` — `makemigrations` (alias `makemigrations`); `pipenv run migrate` — apply them
- `pipenv run test` — Django tests (needs the database up); `pipenv run check`; `pipenv run dbcheck` prints `postgresql`

Before calling backend work done: `pipenv run check && pipenv run python manage.py makemigrations --check --dry-run && pipenv run test`. CI's `backend` job runs the same against a Postgres service.

- Settings come from the gitignored `backend/.env`; every variable is listed in `backend/.env.example`. Add new ones to both.
- `AUTH_USER_MODEL` is `accounts.User` (`AbstractUser` + nullable unique `firebase_uid`, `phone_number`). Roles belong on property membership, never on the user.
- Auth is Firebase ID tokens (`Authorization: Bearer`) verified in `accounts/firebase.py`, the only module that imports `firebase_admin`; it raises its own `InvalidFirebaseTokenError` (→ 401) or `FirebaseUnavailableError` (→ 503, never reported as a bad login). Never trust a UID or phone number from the request body. Admin keeps Django's session login.
- DRF requires authentication by default; a public endpoint opts out with `AllowAny` and `authentication_classes([])` (only `/api/v1/health/` today). CORS is not authentication.
- **Sign-in is invite-only.** A person (`accounts.User`, "People" in admin, with one optional `name` field rather than first/last names, displayed as "Name — +91 …") is linked to a Firebase identity when an admin adds them with a mobile number (`accounts/services.py` `link_firebase_identity`, the last step of the admin save, inside its transaction). Changing or removing a linked number revokes the identity's sessions, and the API refuses people without a number (like admin's "can sign in"), so a removed person's existing token stops working. A verified number nobody added gets 403 `not_registered` and creates nothing; never create or match people by phone at sign-in. Mobile numbers are unique E.164 validated by `accounts/phone.py`, which mirrors `src/utils/phoneCountries.ts` (change both).
- **Access comes only from an active `PropertyMembership` of an active `Property`**, granted in admin (which records `granted_by`). Memberships are ended (inactive), never deleted. Admin portal access (`is_staff`) and app sign-in are separate permissions on one person; admins get no API access without a membership. Role permissions live in `properties/roles.py` (`role_can`), never in Django Groups (hidden: they're global, not per property). Scope every property query through `properties/queries.py` `properties_for_user` (filter the queryset, so others' records 404 and never appear in lists), not object permissions alone.
- API JSON is camelCase with explicit serializer fields; never expose whole models.
- **Tenants are tenancies** (`properties.Tenancy`): one occupant of one flat over a period, with its own UUID, so a flat has many tenancies over time and bills will belong to the tenancy. Status (upcoming/current/ended) is derived from the dates on the India business date (`business_date()`), never stored; end dates are inclusive. Validation lives on the model (admin uses it) with database check constraints behind it; overlapping tenancies of one flat are refused by `clean()` (naming the clash) and, against simultaneous saves, by a PostgreSQL exclusion constraint (`btree_gist`; model validation skips it via `get_constraints` so the message isn't repeated). The tenancy API is read-only and nested under the property (`/api/v1/properties/{id}/tenancies/`), found through `properties_for_user` first. Tenants never sign in.
- Apps: `accounts`, `properties` (properties, memberships, tenancies), `billing` (no models yet). Tests in `tests.py` or a `tests/` package per app; mock `verify_firebase_token`, never call live Firebase.
- Add packages with `pipenv install <name>` and commit `Pipfile.lock`.

## Architecture

Layering, top to bottom — each layer only calls the one below it:

- `views/` — route-level screens. Own navigation (`router.push`) and wire stores to components.
- `components/<feature>/` — forms and UI. Take props, emit events; no router, no service calls.
- `stores/` — Pinia setup stores for **shared** state only. Components change state through store actions, not by assigning store refs.
- `services/` — the only place that talks to external systems (Firebase, the Django API, later Google Sheets). Return app types from `types/`, never vendor types (e.g. `AuthUser`, not a Firebase user), and throw app errors (`AuthError`, `ApiError`), never Firebase or Axios errors.
- `types/`, `utils/` (pure functions), `layouts/`.

`components/ui/` is generated by shadcn-vue (`npx shadcn-vue@latest add <name>`). Don't hand-edit unless necessary.

## Testing

**Every new component, store, util or feature ships with tests in the same change.** When changing existing behaviour, update or add the tests that cover it.

- Vitest + `@vue/test-utils` in jsdom. Tests live next to the code in `__tests__/` (e.g. `src/utils/__tests__/date.spec.ts`), named `*.spec.ts`.
- Components: mount with props, assert rendered output and emitted events — not internal state.
- Stores: use `setActivePinia(createPinia())` in `beforeEach`; test through actions and getters.
- Services/utils: plain input → output, including invalid input.
- Skip `components/ui/` (generated). Test files are linted with `@vitest/eslint-plugin`.

## Conventions

- Import via `@/` alias, not relative `../../`.
- Use theme tokens (`bg-background`, `text-muted-foreground`, `text-destructive`) rather than raw colours.
- Phone numbers are stored as E.164 (`+918341413827`); format for display only (`utils/phone.ts`).
- Login accepts India, Australia and US mobiles. Countries live in one table (`utils/phoneCountries.ts`) that drives validation, input grouping, display and the login country picker; add a country there (and its flag in `components/brand/CountryFlag.vue`).
- Errors are shown inline (`role="alert"`), never `alert()`.
- Motion lives in `style.css`: `animate-page-in` (layout content, so every screen eases in), `animate-rise-in` (content that appears or changes in place; key the element to replay it) and a press-in on every `[data-slot=button]`. All of it is off under `prefers-reduced-motion`; don't hand-edit `components/ui/` for motion.
- `VITE_*` env vars are public — never put secrets in them.

## Current state

Sign-in is **Firebase phone auth** (`services/auth.service.ts`, the only module importing `firebase/auth`; the app is created lazily in `services/firebase.ts` from `VITE_FIREBASE_*` in `.env.local`). Firebase keeps the session itself and restores it **asynchronously**: `authStore.init()` subscribes once and resolves on the first auth state, `ready` says it has, and the route guards `await` it before deciding. Missing config leaves the app signed out with `loginNotice` shown on login. `LoginView` and `VerifyOtpView` each render a `recaptcha-host` element that they pass to `sendOtp` (resend needs a fresh check); the service uses a new container per attempt and clears it after. The pending confirmation and phone number live **in memory**, so refreshing `/verify` returns to login. Firebase errors map to `AuthErrorCode` (`services/authErrors.ts`) and the store words them; an outage is never shown as a wrong code. `App.vue` watches the auth user: if Firebase ends the session elsewhere (another tab, disabled account) it clears per-user state and leaves protected pages.

**Signing in is not access.** Only numbers an admin added can use the app: if `/me` answers 403 `not_registered`, the access store ends the Firebase session (`authStore.endSession`) and login explains why. After sign-in the app calls `GET /api/v1/me/` through `services/api.ts` (Axios; a request interceptor attaches `Authorization: Bearer <ID token>` from `authService.getIdToken()`, which Firebase caches and refreshes; never store the token). `stores/access.ts` holds the identity and the selected property: one property is selected automatically, several need a choice, none means "no property access", and a failed load is an **error with Retry**, never no access. Routes with `meta.requiresProperty` (dashboard and tenant pages) redirect to `/properties` (`PropertySelectView`, with `?redirect=` to return; only same-app paths are followed) until a property is selected. Property selection is separate from tenant selection. Guards are UX only: the backend enforces authentication and property access.

In development `/api` is proxied to Django on `127.0.0.1:8000` (`vite.config.ts`), so the app calls its own origin and needs no CORS setup; `VITE_API_BASE_URL` overrides it. Granting access is manual (backend README "Granting access"): sign in once, then add an owner membership in Django admin.

Logout (`composables/useLogout.ts`) clears the selected tenant and property access, then `signOut()`s. **Saved entries are not per user:** one global localStorage key that logout keeps, so the next account on the browser sees them. Move entries to the backend (or namespace them by user) before real multi-user use.

Tests never touch Firebase or the API: mock the services with the shared fakes, `vi.mock('@/services/auth.service', () => import('@/test/mocks/authService'))` and the same for `access.service` and `tenant.service`, calling `resetAuthService()`/`resetAccessService()`/`resetTenantService()` in `beforeEach`. The tenant fake searches and pages its fictional `testTenants` (ids `tenant-001`…) like the API; `fakeTenancies` changes them or the page size, and `loadTestTenants()` (`src/test/tenants.ts`) signs in, selects the property and loads them for store tests. `signInAs()` sets the session Firebase "restores"; the default identity has one property, so protected pages open directly. The router is shared across tests: navigate with `force: true` when the path may already be current.

Tenants come from the backend's **tenancies** of the selected property (`services/tenant.service.ts`, which validates each response as a `TenancyDto` and maps it to the app's `Tenant`, converting the decimal-string money to numbers; `Tenant.id` is the tenancy UUID). `stores/tenant.ts` keeps the search **results** (current tenancies only, paginated with Load more, for the query they answer) apart from a **cache of tenants by id**, which also holds tenants loaded by id; `selectedTenant` comes from the cache, so a search that leaves the selected tenant out never loses it. The selector searches through the API 300 ms after typing pauses (`TenantSelector` emits `search`); every list request is numbered and only the newest may change state, so an older response never replaces a newer search. Changing the selected property (switching, logout, lost access) resets the tenant store at once (a sync watcher in the store) and discards pending responses. A failed load is an error with Retry, never "No current tenants found." Pages opened by URL load their tenant through the detail API (`loadTenant`, any status), so they never depend on visiting the dashboard. The dashboard never auto-selects a tenant. Below the selected tenant's name it shows their latest bill by billing month (`LatestEntryCard`, via `TenantDetails`' `latest-entry` slot) once entries have loaded, and nothing when they have none or failed to load. Format money with `utils/currency.ts` (`formatINR`) and days with `utils/date.ts` (`formatOrdinal`).

**Local bills and backend tenants are not linked.** Entries keep the `tenantId` they were saved with: entries saved before this change carry the old mock ids (`tenant-001`) and show under no backend tenancy; new ones carry tenancy UUIDs. Never match records by tenant name and never upload local entries automatically; importing them needs an explicit id mapping (BE Phase 4 moves bills to the backend).

Rent entries (`types/rentEntry.ts`, the **charges** of one bill) and payments (`types/payment.ts`, **money received** against one bill) are separate records. A bill can have several payments; they're never allocated across months. They persist together, with payment receipts, in **localStorage** as one ledger (`utils/rentLedgerStorage.ts`, wrapper `types/rentLedger.ts`, `version: 3`) written with a single `setItem`, so a bill and its initial payment save together or not at all. The key is still `rent-tracker:rent-entries:v1`; the wrapper's `version` decides how it's read. Older versions are migrated on load, validated, and written back as version 3 before state updates; if that fails the original data stays untouched and a load error shows. Version 1 data (one `totalPaid`/`paidDate` on the entry) becomes a payment with id `legacy-payment:<entryId>` (its amount rounded to whole paise: version 1 allowed any decimals); version 2 data gains `receipts: []` (migration never issues receipts). One browser, prototype only, one bill per tenant per billing month. Loading validates every record with the shared rules (`utils/rentEntryValidation.ts`, `utils/paymentValidation.ts`) plus ledger relationships (unique ids, no orphan payments, payments never exceed the bill) and **throws** on bad data; never treat that as an empty list, or the next save overwrites the user's data. `stores/rentEntry.ts` `initialize()` is called by every page that needs entries (it's idempotent and doubles as Retry); `loadError` blocks saving. Every write (`addEntry`, `addPayment`) validates, re-reads storage right before writing (other tabs may have saved; writing a stale copy would erase their records), then writes before updating state, so a failed write never shows as saved. `addPayment` recalculates the outstanding balance from storage and rejects a reused payment id: `RecordPaymentForm` generates one id per form and reuses it on retry. This assumes one active tab; real concurrency needs the backend. A `storage` listener reloads entries changed by another tab. Logout never clears saved entries: don't use `localStorage.clear()`.

Entries store rent and electricity rate as historical values; total due, total paid (always the sum of the bill's payments, `getTotalPaid`), outstanding and payment status are derived with `utils/rentCalculations.ts`, never stored or typed in. Money is compared and summed as integer paise (`utils/money.ts`); payment amounts allow at most two decimals. `RentEntryForm` keeps the draft locally and emits a validated `NewRentEntrySubmission` (the bill plus an optional initial payment, `null` when 0); `NewRentEntryView` (`/tenants/:tenantId/entries/new`) saves it and confirms before discarding unsaved changes. Further payments are recorded from the details page (`RecordPaymentForm` in a `Dialog`, with a projected balance); a fully paid bill shows "Fully paid" instead. Overpayments are rejected, editing/deleting payments is deferred, and previous balances are not carried forward yet.

Receipts (`types/receipt.ts`, `PaymentReceipt`) confirm **one payment**, never the bill: the amount is that payment's. Each payment has at most one, issued by `issueReceipt(paymentId)`, which returns the existing receipt if there is one and writes before updating state (a failed write leaves the payment recorded and shows inline). A receipt is a **snapshot** taken at issue time (the issue date as printed, so it never depends on the downloader's time zone; issuer from `config/receiptIssuer.ts`; tenant name, flat, mobile and deposit; the bill's charges and rent due day; total due, paid and outstanding as they stood right after this payment; last month's outstanding, shown for information only; the payment's amount/date/notes), so later payments or changed tenant/issuer details never change it; never re-derive it from current data. Its reference is `RCP-<flat>-<YYYYMM>`, with `-<n>` for a bill's nth payment (`receiptReferenceFor`), falling back to one with the payment id on a clash, and is never regenerated. The issuer's personal details (manager, address, phone, email) come from `VITE_RECEIPT_ISSUER_*` in the gitignored `.env.local` (see `.env.example`); they're baked in at build time, so changing them needs a rebuild. Loading checks receipt shape and relationships (unique ids/references, one per payment, its payment belongs to its entry, amount and paid date match the payment, charges match the bill and its figures add up) but never compares the tenant or issuer snapshots with current details. Without `.env.local` the address is a placeholder, and production builds refuse to issue receipts (`utils/receiptValidation.ts`).

Receipts are **downloaded as PDFs**; there's no receipt page. `composables/useReceiptDownload.ts` issues the receipt (or reuses it) and calls `downloadReceiptPdf` (`utils/receiptDownload.ts`), which lazy-loads jsPDF and the Poppins TTFs (`@expo-google-fonts/poppins`; the PDF standard fonts have no ₹) on first use. `utils/receiptContent.ts` works out what the receipt says from the snapshot alone (and the file name, e.g. `Mirza Baig 102 Rent September 2026 RCP-102-202609.pdf`); `utils/receiptPdf.ts` only lays that out as real, selectable text on A4, on one page for any receipt within the field limits. Download buttons: the entry's payment history (Download receipt, per payment), the new-entry confirmation (Download Receipt, initial payment) and Previous Entries (Download Receipt beside View Summary, for the bill's latest recorded payment; bills with no payment get none). They show "Preparing…" while busy, never claim the file was saved, and show failures inline (a PDF failure keeps the issued receipt, so a retry reuses it).

History (`/tenants/:tenantId/entries`, `RentEntryHistoryView`) and details (`/tenants/:tenantId/entries/:entryId`, `RentEntryDetailsView`) take the tenant from the URL, never the dashboard selection, and the details page matches the entry on **both** ids so an entry never shows under another tenant. Both load tenants and entries themselves so direct links and refreshes work, and show a load error instead of empty or zero states when entries fail to load. Tenant pages opened by URL (new entry, history, details) get their tenant from `composables/useRouteTenant.ts`, which reports a failed tenant load as an error with Retry, never as "Tenant not found". The router reuses a page when only its params change, so derive from the route props (computeds) rather than loading in `onMounted` alone, and reset page-local state such as filters when the tenant changes. Per-entry figures come from `getEntryAmounts(entry, totalPaid)` and summary totals from `sumEntryAmounts` (`utils/rentCalculations.ts`), so the table, cards and details agree. Totals cover only the displayed (filtered) entries and are labelled that way; the deposit is never applied to them. Back links use explicit routes, not `router.back()`; the details page goes back to Previous Entries unless opened with `?from=dashboard` (the dashboard's latest entry), which returns to the dashboard with that tenant selected.

The owners currently keep everything in a Google Sheet with an Apps Script that emails receipts. Its layout, data problems and what the app needs from it are in `docs/google-sheets-integration.md`; read it before any Sheets work. The script itself lives in `google-api/` (see its README): personal details come from Script Properties and the script ID from the gitignored `.clasp.json`. The owners' WhatsApp bot, a separate Apps Script project that writes monthly entries to the same sheet and is expected to be retired, lives in `whatsapp-bot/` (the sheet ID and its secrets come from Script Properties). The repo is public: never commit the real sheet, tenant data, email addresses, phone numbers or IDs.

Route guards live in `router/index.ts` (`meta.requiresAuth`, `meta.guestOnly`, `meta.requiresProperty`) and are async: they wait for `authStore.init()` and, for property routes, `accessStore.load()`. Pinia is installed before the router in `main.ts` so guards can use stores.
